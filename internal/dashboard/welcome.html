Get Started

01Get a key

One key works on both routes. Ask a gateway admin — Noy Itzikowitz or Yossi Ovadia — for a pk-… key, or sign in to the dashboard with SSO and mint one yourself under My account → API keys.

02Quick start

Two commands to prove everything works, before you touch any config file.

Smoke test with curl

A chat completion on the OpenAI route.

bash
curl {{OPENAI_URL}}/chat/completions \
  -H "Authorization: Bearer $PRICETAG_KEY" \
  -H "content-type: application/json" \
  -d '{"model":"gpt-5.6-luna","messages":[
        {"role":"user","content":"hello from PriceTag"}]}'

Claude Code in two lines

Point it at the unified route and go.

!

If you've used Vertex or BedLab before, leftover variables silently bypass the gateway — run this before the block below, and clear it out of your .zshrc too.

unset CLAUDE_CODE_USE_VERTEX
unset ANTHROPIC_VERTEX_PROJECT_ID
bash
export ANTHROPIC_BASE_URL={{UNIFIED_URL}}
export ANTHROPIC_API_KEY=$PRICETAG_KEY

claude

03Set up Claude Code, properly

Make it permanent in ~/.claude/settings.json and teach the /model picker about the hosted model.

Route the CLI through the gateway

Everything Claude Code needs lives under env — no shell exports required.

~/.claude/settings.json
{
  "env": {
    "ANTHROPIC_BASE_URL": "{{UNIFIED_URL}}",
    "ANTHROPIC_API_KEY": "pk-your-key",
    "CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1"
  }
}

With discovery on, /model reads the gateway's /v1/models — so new Claude models appear with no config change.

Add the hosted model to the picker

Claude Code's model filter only keeps claude/anthropic ids, so discovery alone never shows the hosted Qwen. Pin it explicitly (needs Claude Code ≥ 2.1.242):

~/.claude/settings.json — add
{
  "modelPicker": {
    "options": [
      { "model": "Inferact/Qwen3.8-Flash-Next-NVFP4",
        "label": "Qwen 3.8 Flash Next",
        "description": "Hosted vLLM via PriceTag — $0.15/$0.47 per MTok" }
    ]
  },
  "modelSettings": {
    "Inferact/Qwen3.8-Flash-Next-NVFP4": { "effortLevel": "medium" }
  }
}
!

Use the model id exactly as shown — on the unified route an unknown id falls through to Anthropic and 404s. And keep effortLevel at "medium": the hosted endpoint accepts low/medium/xhigh and rejects "high".

04Set up Codex

Codex speaks OpenAI Responses, so setup is one provider block per route: GPT on the OpenAI route, hosted Qwen on the unified route. GPT first — the lineup (gpt-5.x) including gpt-5.3-codex:

~/.codex/config.toml
# provider: PriceTag gateway
[model_providers.pricetag]
name     = "PriceTag"
base_url = "{{OPENAI_URL}}"
env_key  = "PRICETAG_KEY"
wire_api = "responses"

[profiles.pricetag]
model          = "gpt-5.3-codex"
model_provider = "pricetag"
export PRICETAG_KEY=pk-your-key
codex --profile pricetag

And the hosted Qwen — a second provider pointed at the unified route, which serves /v1/responses for it too:

~/.codex/config.toml — add
[model_providers.qwen]
name        = "PriceTag hosted"
base_url    = "{{UNIFIED_URL}}"
wire_api    = "responses"
http_headers = { "x-api-key" = "pk-your-key" }  # the unified route wants the key here, not as a bearer token

[profiles.qwen]
model          = "Inferact/Qwen3.8-Flash-Next-NVFP4"
model_provider = "qwen"
# Codex has no built-in metadata for this model id; without this it warns
# "Model metadata not found" and falls back to a tiny window. 262144 = 256K.
model_context_window = 262144
codex --profile qwen
✓

One catch: Codex only shows its own built-in models in the /model picker, so pin the hosted model id in the profile as above — it works, it just won't appear in the list. The model_context_window line is what silences the "Model metadata not found" warning on start.

05Set up OpenCode

Re-aim OpenCode's built-in anthropic and openai providers at the gateway. Keep them built-in on purpose: OpenCode only pulls the model chooser and effort levels from models.dev for official provider ids, so overriding options — instead of adding a custom provider — keeps every model and setting available in the picker.

opencode.json (project root)
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "anthropic": {
      "options": { "baseURL": "{{UNIFIED_URL}}/v1", "apiKey": "{env:PRICETAG_KEY}" }
    },
    "openai": {
      "options": { "baseURL": "{{OPENAI_URL}}", "apiKey": "{env:PRICETAG_KEY}" }
    },
    "pricetag-hosted": {
      "npm": "@ai-sdk/anthropic",
      "name": "PriceTag (hosted)",
      "options": { "baseURL": "{{UNIFIED_URL}}/v1", "apiKey": "{env:PRICETAG_KEY}" },
      "models": {
        "Inferact/Qwen3.8-Flash-Next-NVFP4": {
          "name": "Qwen 3.8 Flash Next (hosted)",
          "limit": { "context": 262144, "output": 8192 }
        }
      }
    }
  },
  "model": "anthropic/claude-sonnet-5"
}

Switch models inside OpenCode with /models — anthropic/… and openai/… now ride the gateway (billed like everything else), and pricetag-hosted/… runs on our vLLM at hosted rates. Don't want to touch the config file? OpenCode also merges the OPENCODE_CONFIG_CONTENT env var, which takes the same JSON as a string.

!

Two traps, both silent: the Anthropic SDK appends /messages to baseURL, so it needs the /v1 suffix (host root hits /messages and fails) — the OpenAI SDK appends /chat/completions, which is why {{OPENAI_URL}} already ends in /v1. And don't point the built-in anthropic provider at the OpenAI route: its catalog has no claude-* ids, so requests die with "model does not exist or you do not have access to it".

06Set up Hermes CLI

Hermes takes the gateway as one provider per dialect, same rule as everywhere else: the GPT lineup on a custom OpenAI-compatible endpoint, the hosted Qwen on the built-in anthropic provider re-aimed at the unified route. The choice is saved under model: in ~/.hermes/config.yaml — the hermes model wizard writes it, or edit it directly:

~/.hermes/config.yaml — GPT lineup (OpenAI dialect)
model:
  provider: "custom"
  default:  "gpt-5.3-codex"
  base_url: "{{OPENAI_URL}}"   # already ends in /v1
~/.hermes/config.yaml — hosted Qwen (Anthropic dialect)
model:
  provider: "anthropic"
  default:  "Inferact/Qwen3.8-Flash-Next-NVFP4"
  base_url: "{{UNIFIED_URL}}/v1"   # the /v1 suffix is required
~/.hermes/.env — one key, used twice
OPENAI_API_KEY=pk-your-key
ANTHROPIC_API_KEY=pk-your-key

The same PriceTag key works on both lines — the route decides the dialect, not the key. The anthropic provider sends it as x-api-key natively, which is exactly what the unified route reads. Switch providers with hermes model; /model inside a session only switches between providers already set up.

!

Three traps, learned the hard way this week: the OpenAI route has no Qwen ids — asking for one gets "The model … does not exist or you do not have access to it" from upstream, so keep the model id and the base URL as a matched pair, never mix halves. The anthropic provider needs the /v1 suffix on base_url. And Hermes auxiliary tasks (session titles, compression) follow the main model by default — pointing the default at the hosted id means those calls ride on it too.

07Know your routes

Three endpoints, one key. Pick the one that speaks your client's dialect — the path suffixes differ on purpose.

Unified route
Anthropic dialect · POST /v1/messages · no /v1 suffix
{{UNIFIED_URL}}
Everything Claude Code and other Anthropic-dialect clients expect. Routes claude-* to the real Anthropic API and the hosted Qwen* ids to our own vLLM — same URL, switch models freely. "Unified" means unified backends, not unified dialects: this route only speaks Anthropic format (x-api-key) — OpenAI-format clients with Bearer tokens belong on the OpenAI route below.
x-api-key: pk-…
OpenAI route
OpenAI dialect · POST /v1/chat/completions · base URL ends in /v1
{{OPENAI_URL}}
For Codex, OpenCode and any OpenAI-compatible client. Covers the GPT lineup (gpt-5.x) only — there are no claude-* or Qwen ids here, and asking for one gets "The model … does not exist or you do not have access to it" from upstream. Those models live on the unified route.
